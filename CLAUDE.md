# CLAUDE.md — инструкция Claude Code на каждую сессию

## Источник истины

**`SPEC.md`** в корне репозитория — единственный и полный источник истины для проекта.
Любое расхождение между этим файлом и `SPEC.md` решается в пользу `SPEC.md`.

Перечитывай релевантные разделы `SPEC.md` перед началом работы над фазой:
- §8 — структура папок
- §9 — точные версии зависимостей
- §10 — конфиги (tsconfig, electron.vite, electron-builder, eslint, prettier)
- §11 — roadmap фаз
- §12 — детальный TODO-лист (твой план работы)
- §14 — Troubleshooting (читать ПЕРВЫМ при любой ошибке)
- §17 — финальные инструкции

## Жёсткие правила (нарушать нельзя)

1. **Atomic commits** — 1 TODO-пункт из §12 = 1 коммит. Никаких «оптом».
2. **Conventional commits** с префиксом фазы:
   - `feat(p2): add Konva transformer`
   - `fix(p5): EMU rounding off-by-one`
   - `test(p4): timeline build`
   - `chore(p1): bootstrap project files`
3. **После каждого пункта** запускай:
   ```bash
   npm run typecheck && npm run lint
   ```
   Коммит только если оба зелёные. Если красные — чини в том же пункте, не оставляй на потом.
4. **Комментарии в коде — только на русском**. Идентификаторы (имена переменных, функций, типов, файлов) — только на английском.
5. **Запрещённые зависимости:**
   - AGPL-лицензированные (OnlyOffice DocServer, PPTist, любые AGPL-форки).
   - tldraw 4.x (платная коммерческая лицензия).
   - officegen (заброшен).
   - Любые «cloud-only» или telemetry-зависимые библиотеки.
6. **Не задавай уточняющих вопросов пользователю** — все решения уже в `SPEC.md`. При неопределённости — см. ниже.
7. **Не запускай dev-сервер и не собирай .exe без прямой просьбы** — это длинные операции, пользователь сам инициирует.
8. **Не создавай файлы документации** (`*.md`, `README*`) за пределами тех, что описаны в этом репозитории, если пользователь явно не попросил.
9. **Смоук-тесты — небольшие, но обязательные.** Не пропускай проверку фичи: добавляй короткий smoke в `TESTS.md` для нового пункта и/или фокус-тест в `tests/unit`. Зелёные typecheck/lint/test ещё не значат, что фича реально работает. **После реализации присылай смоук-тест(ы) нового пункта прямо в чат** — пользователь прогоняет их вручную (dev-сервер запускает сам).
10. **Отчёт о сделанном — 1-2 предложения, по делу** (что изменилось + что дальше). Без длинных списков, если пользователь не попросил.

## Порядок работы в каждой сессии

1. Прочитать `PROGRESS.md` → найти текущую фазу и первый неотмеченный `[ ]` пункт.
2. Прочитать соответствующий раздел `SPEC.md` (§12 для TODO, §6/§5 для технических деталей пункта).
3. Реализовать пункт:
   - написать код (+ тесты, если фаза этого требует — см. §11/§12).
   - запустить `npm run typecheck`.
   - запустить `npm run lint`.
   - починить, если красное.
4. `git add <конкретные файлы>` (не `-A`) → `git commit -m "feat(pN): ..."`.
5. Отметить пункт в `PROGRESS.md` как `[x]` (тем же или следующим коммитом, как удобнее — но не забывать).
6. Перейти к следующему пункту.
7. В конце фазы:
   - `npm run typecheck && npm run lint && npm test` (+ `npm run build` если уместно).
   - `git tag phaseN-complete`.
   - Остановиться и уведомить пользователя, что фаза готова.

## Что делать при неопределённости

**НЕ задавай вопросов пользователю.** Действуй так:

1. Перечитай релевантный раздел `SPEC.md` ещё раз — обычно ответ там есть.
2. Если действительно нет — прими разумное минимальное решение (наименьшая сложность, наименьшее отклонение от духа спеки).
3. **Запиши решение в `DECISIONS.md`** в формате:
   `Дата | Контекст | Решение | Обоснование`.
4. Продолжай работу. Пользователь увидит запись и при желании откатит.

Принцип: лучше быстро принятое отменяемое решение, чем заблокированный прогресс.

## Что делать при ошибке/баге

Порядок диагностики, без пропусков:

1. **§14 `SPEC.md` Troubleshooting** — там 15 типовых проблем (electron-rebuild, Konva fonts, printToPDF, fast-xml-parser, PptxGenJS, file://, NSIS, fileAssociations, SmartScreen, memory leak, spell check, видео-кодеки, TS6 refs, GSAP+Konva, .pptx round-trip). Сначала ищи свою ситуацию здесь.
2. Если в §14 нет — обдумай первопричину сам (имитация «погуглить»): прочитай сообщение об ошибке, посмотри стек, посмотри документацию ближайшей библиотеки, выдвини гипотезу, проверь её минимальным тестом.
3. Если за разумное время (≈3–4 попытки) не получилось — **запиши в `BUGS.md`** в формате:
   `Дата | Фаза/Пункт | Описание | Воспроизведение | Статус`.
   Статус = `OPEN`. Двигайся дальше по плану, если пункт не блокирует следующие; иначе остановись и уведоми пользователя.

## Git и ветки

- Рабочая ветка этой сессии: `claude/setup-project-files-RFewL` (задана хостом).
- Не пушить в `main` без явной команды.
- Перед `git push` — `git push -u origin <branch>`; при сетевой ошибке retry до 4 раз (2s/4s/8s/16s).
- **НИКОГДА** не `git push --force`, `git reset --hard`, `git clean -f`, `git branch -D` без явной команды пользователя.
- Не амендить уже запушенные коммиты — создавай новые.
- Не пропускать pre-commit хуки (`--no-verify` запрещено).

## Связанные файлы

- `SPEC.md` — спецификация (источник истины).
- `PROGRESS.md` — чеклист фаз и пунктов; отмечать `[x]` по мере выполнения.
- `DECISIONS.md` — журнал принятых решений при неопределённости.
- `BUGS.md` — журнал нерешённых проблем/блокеров.
- `TESTS.md` — 30 ручных smoke-тестов, которые прогоняет пользователь после каждой фазы.
- `README.md` — короткая инструкция для пользователя.
